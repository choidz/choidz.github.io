# PostgreSQL 데드락 오류 해결 방법

## 증상 및 오류 메시지
PostgreSQL에서 작업을 수행할 때, 다음과 같은 오류 메시지를 자주 접할 수 있습니다:

```
ERROR: deadlock detected
DETAIL: Process 1234 waits for ShareLock on transaction 5678; blocked by process 4321.
        Process 4321 waits for ShareLock on transaction 8765; blocked by process 1234.
```

이 메시지는 두 개의 트랜잭션이 서로의 잠금을 기다리며 멈춰 있는 상태를 나타냅니다. 이러한 상황을 데드락이라고 하며, PostgreSQL은 이를 자동으로 감지하여 한쪽 트랜잭션을 롤백합니다. 하지만 이로 인해 데이터베이스의 성능이 저하되고, 사용자 경험에 부정적인 영향을 미칠 수 있습니다.

## 데드락의 원인
데드락은 여러 원인으로 발생할 수 있습니다. 주요 원인은 다음과 같습니다:

1. **순환 대기(Circular Wait):** 두 개 이상의 트랜잭션이 서로의 자원을 기다리며 발생하는 상황입니다. 예를 들어, 트랜잭션 A가 자원 X를 잠그고 자원 Y를 기다리며, 트랜잭션 B가 자원 Y를 잠그고 자원 X를 기다리는 경우가 이에 해당합니다.

2. **잠금 순서의 불일치:** 여러 트랜잭션이 자원을 잠그는 순서가 다를 경우 발생할 수 있습니다. 예를 들어, 트랜잭션 A가 자원 1을 먼저 잠그고, 자원 2를 잠그려 할 때, 트랜잭션 B가 자원 2를 먼저 잠그고 자원 1을 기다리면 데드락이 발생합니다.

## 진단 방법
데드락을 진단하기 위해서는 다음과 같은 방법을 사용할 수 있습니다:

1. **에러 메시지 확인:** 에러 메시지의 `DETAIL` 부분을 확인하여 어떤 프로세스가 어떤 자원을 기다리고 있는지 파악합니다.

2. **`pg_locks`와 `pg_stat_activity` 조회:** 현재 데이터베이스에서 어떤 트랜잭션이 어떤 잠금을 쥐고 있는지 확인하기 위해 다음과 같은 SQL 쿼리를 실행합니다:
   
   ```sql
   SELECT * FROM pg_locks;
   SELECT * FROM pg_stat_activity;
   ```
   이 쿼리를 통해 현재 잠금 상태와 트랜잭션 정보를 확인할 수 있습니다.

3. **로그 설정:** `log_lock_waits`를 활성화하여 잠금을 기다리는 상황을 로그에 기록하도록 설정합니다. 이를 통해 데드락 발생 직전의 상황을 추적할 수 있습니다.
   
   ```sql
   SET log_lock_waits = on;
   ```

## 해결 절차
데드락 문제를 해결하기 위해서는 다음과 같은 절차를 따릅니다:

1. **잠금 순서 통일:** 모든 트랜잭션이 자원을 항상 같은 순서로 잠그도록 코드 로직을 수정합니다. 예를 들어, 여러 행을 잠글 때 항상 ID 오름차순으로 처리합니다.
   
   ```sql
   SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
   ```

2. **트랜잭션 단축:** 트랜잭션의 범위를 최소화하여 잠금을 짧게 유지합니다. 트랜잭션 안에서 느린 작업을 피하고, 데이터베이스 작업만 포함시킵니다.

3. **재시도 로직 추가:** 데드락이 발생할 경우, 해당 트랜잭션을 재시도하는 로직을 추가합니다. 예를 들어, 다음과 같은 비동기 함수로 구현할 수 있습니다:
   
   ```typescript
   async function withDeadlockRetry(fn, max = 3) {
     for (let i = 0; ; i++) {
       try {
         return await fn();
       } catch (e) {
         if (e.code === '40P01' && i < max) continue;
         throw e;
       }
     }
   }
   ```

4. **잠금 범위 축소:** 필요 이상으로 넓게 잠그지 않도록 인덱스를 활용하여 잠금 범위를 좁힙니다. 이를 통해 잠금 충돌 확률을 줄일 수 있습니다.

## 재발 방지 체크리스트
데드락을 예방하기 위해 다음과 같은 체크리스트를 활용할 수 있습니다:

- [ ] 모든 트랜잭션이 자원을 동일한 순서로 잠그는가?
- [ ] 트랜잭션의 범위가 최소화되어 있는가?
- [ ] 데드락 발생 시 재시도 로직이 구현되어 있는가?
- [ ] 잠금 범위가 최소화되었는가?

이러한 방법들을 통해 PostgreSQL에서의 데드락 문제를 효과적으로 해결하고 예방할 수 있습니다. 데드락은 복잡한 문제일 수 있지만, 체계적인 접근을 통해 충분히 관리할 수 있습니다.

## 실무 적용 체크리스트

- PostgreSQL deadlock detected 해결을 적용하기 전에 현재 운영 환경의 기준값과 예외 상황을 먼저 정리합니다.
- 변경 전후로 확인할 지표를 정하고, 문제가 생겼을 때 되돌릴 수 있는 절차를 문서화합니다.
- 한 번에 모든 서버나 서비스에 적용하기보다 작은 범위에서 검증한 뒤 점진적으로 확대합니다.
- 담당자, 확인 시간, 장애 판단 기준을 명확히 남겨 같은 문제가 반복될 때 빠르게 대응할 수 있게 합니다.
