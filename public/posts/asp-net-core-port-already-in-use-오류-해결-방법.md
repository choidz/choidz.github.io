# ASP.NET Core 'port already in use' 오류 해결 방법

## 증상 및 오류 메시지
ASP.NET Core 애플리케이션을 실행할 때 'port already in use'라는 오류 메시지를 자주 접할 수 있습니다. 이 오류는 특정 포트가 이미 다른 프로세스에 의해 사용 중일 때 발생합니다. 예를 들어, 다음과 같은 메시지를 볼 수 있습니다:

```
Address already in use
```
이 메시지는 해당 포트를 사용할 수 없음을 나타내며, 애플리케이션이 정상적으로 시작되지 않습니다. 이 문제는 개발 환경에서 자주 발생할 수 있으며, 특히 여러 개의 서버를 동시에 실행할 때 주의가 필요합니다.

## 원인
이 오류의 주된 원인은 애플리케이션이 사용할 포트가 이미 다른 프로세스에 의해 점유되고 있기 때문입니다. 일반적으로 다음과 같은 상황에서 발생합니다:
1. **이전 인스턴스의 잔여 프로세스**: 애플리케이션이 비정상적으로 종료되었거나, 이전 인스턴스가 여전히 실행 중일 경우입니다.
2. **다른 애플리케이션의 충돌**: 동일한 포트를 사용하는 다른 애플리케이션이 실행 중일 수 있습니다.
3. **포트 설정 오류**: 잘못된 포트 번호를 지정했거나, 설정 파일에서 포트 번호가 중복되는 경우입니다.

## 확인 명령어
현재 어떤 프로세스가 해당 포트를 사용 중인지 확인하기 위해 다음 명령어를 사용할 수 있습니다. Windows에서는 `netstat` 명령어를 사용하고, Linux에서는 `lsof` 명령어를 사용합니다.

### Windows
```bash
netstat -ano | findstr :<포트번호>
```
### Linux
```bash
lsof -i :<포트번호>
```
이 명령어를 실행하면 해당 포트를 사용 중인 프로세스의 PID를 확인할 수 있습니다. 이 정보를 통해 어떤 프로세스가 포트를 차지하고 있는지 파악할 수 있습니다.

## 해결 절차
이제 문제를 해결하기 위한 절차를 살펴보겠습니다. 다음 단계를 따라 진행하면 됩니다:
1. **포트 사용 프로세스 종료**: 확인된 PID를 사용하여 해당 프로세스를 종료합니다.
   - Windows:
   ```bash
   taskkill /PID <PID> /F
   ```
   - Linux:
   ```bash
   kill -TERM <PID>
   ```
2. **포트 변경**: 애플리케이션의 포트를 변경하고 다시 실행합니다. 로컬 개발에서는 `Properties/launchSettings.json`의 `applicationUrl`을 바꿀 수 있습니다. 배포 환경에서는 Kestrel의 URL 또는 엔드포인트 설정을 확인해야 합니다.
   ```json
   "applicationUrl": "http://localhost:<새로운포트번호>"
   ```
3. **서버 재시작**: 애플리케이션을 다시 실행하여 문제가 해결되었는지 확인합니다.

## 흔한 실수
이 오류를 해결하는 과정에서 흔히 발생하는 실수는 포트를 종료한 후에도 애플리케이션을 재실행하지 않는 것입니다. 또한, 포트 변경 후 설정 파일을 저장하지 않거나, 잘못된 포트 번호를 입력하는 경우도 있습니다. 따라서 설정 파일을 수정한 후에는 반드시 변경 사항을 저장하고 애플리케이션을 재시작해야 합니다.

## 재발 방지 체크리스트
1. **포트 관리**: 개발 중 사용하는 포트를 관리하고, 충돌을 피하기 위해 각 애플리케이션에 고유한 포트를 지정합니다.
2. **정상 종료 확인**: 애플리케이션을 종료할 때는 항상 정상적으로 종료되었는지 확인합니다.
3. **모니터링 도구 활용**: 시스템에서 실행 중인 프로세스를 모니터링하는 도구를 사용하여 포트 충돌을 사전에 예방합니다.

이와 같은 방법을 통해 'port already in use' 오류를 효과적으로 해결하고, 향후 발생할 수 있는 문제를 예방할 수 있습니다.

## 실무 적용 체크리스트

- ASP.NET Core port already in use 해결을 적용하기 전에 현재 운영 환경의 기준값과 예외 상황을 먼저 정리합니다.
- 변경 전후로 확인할 지표를 정하고, 문제가 생겼을 때 되돌릴 수 있는 절차를 문서화합니다.
- 한 번에 모든 서버나 서비스에 적용하기보다 작은 범위에서 검증한 뒤 점진적으로 확대합니다.
- 담당자, 확인 시간, 장애 판단 기준을 명확히 남겨 같은 문제가 반복될 때 빠르게 대응할 수 있게 합니다.
